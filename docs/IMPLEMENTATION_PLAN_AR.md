# ديمة — خطة البناء التفصيلية

> قرار المستخدم الأحدث، 31 أكتوبر 2026: تنفيذ الويب كاملًا بأسلوب Waterfall؛ إغلاق ومراجعة كل مرحلة قبل التالية. الهاتف وM0/M1/M2 خارج النطاق الحالي، ولا تعطل مراحل الويب. [الحالة الفعلية](STATUS_AR.md) و[خطة التنفيذ الحالية](WEB_WATERFALL_AR.md) تتقدمان على أي وصف تاريخي أدناه.

## الهدف وطريقة العمل

إطلاق نسخة ويب تحقق P0 في [PRD](PRD_AR.md): حسابات، كورسات وخطط، استدراك، تركيز فردي وجماعي، تقدم ومشاركة اختيارية، مع حفظ موثوق وتشغيل قابل للاستعادة. لا تنفيذ للهاتف حاليًا؛ يُحفظ [قرار Android السابق](ANDROID_DECISION_AR.md) كمرجع تاريخي مؤجل.

نبدأ بأساس صغير، ثم كل مرحلة تضم البيانات والصلاحيات والـAPI والواجهة والاختبارات اللازمة. لا نبني كل الباك إند منفصلًا عن تجربة المستخدم، ولا نعتبر الشاشات ببيانات وهمية إنجازًا وظيفيًا.

أول تسليم مفيد: دخول ← اختيار/إضافة كورس ← تحديد السابق والسعة ← معاينة خطة ← Today ← إكمال نشاط ← ظهوره من جهاز آخر. Work-only له مسار مباشر للتركيز دون إجباره على كورس.

المراجع الحاكمة: PRD للنطاق، Screens للتنقل، Recovery للتخطيط والتقدم، Rooms للوقت والحضور، Architecture للصلاحيات والمعاملات، Delivery للاختبارات. هذه الخطة تفصّل B0–B7 القائمة وتضيف M0/M1/M2؛ لا تستبدل العقود الوظيفية.

## ما نعرفه وما يلزم اختباره

- مجلد المشروع كان Git فقط وقت الفحص؛ الوثائق الحالية نُسخت إليه، ولم يوجد package.json أو تطبيق إنتاجي.
- الهوية واللاندنج والنموذج المحلي موجودة في حزمة UI القديمة. هي مرجع وأصول لإعادة الاستخدام، وليست React أو باك إند جاهزًا. تُراجع تراخيصها؛ لا نشتري مكونات جديدة تلقائيًا.
- الاستضافة المعتمدة Cloudflare Workers + Supabase Free، والدومين dima.study لدى Spaceship حسب إفادة المستخدم. وجود تبويبات مفتوحة ليس إعدادًا مثبتًا أو تفويضًا للنشر.
- مسار Next على Workers، ميزانية CPU، وطريقة بناء عميل Android وإضافاته تُحسم باختبارات صغيرة. لا نسب إعادة استخدام أو موعد تسليم أو مجانية دائمة مضمونة.
- المستخدم وافق على تسجيل مسار Android؛ إصدار Android الكامل لاحق، بينما اختبارات الجدوى ضمن التحضير والبناء.

## تنظيم الملفات المقترح عند بدء الكود

الجدول التالي تصميم مستهدف؛ أنشأ B0 apps/web وpackages/contracts/client/ui وsupabase/tests/scripts. أنشأ apps/client-proof لبناء عميل مستقل، وليس apps/mobile أو packages/domain حتى الآن. التفاصيل الفعلية في دليل B0:

| المسار داخل المشروع | المسؤولية |
|---|---|
| `apps/web/` | Next: الموقع العام وواجهة العضو والإدارة ومسارات `/api/v1` |
| `apps/web/src/server/` | وحدات المجال والتفويض والتكامل مع DB؛ تبقى على السيرفر |
| `packages/contracts/` | مخططات الطلبات/الردود والأخطاء والتحقق وعقد API |
| `packages/domain/` | حسابات التخطيط الخالصة بلا Next/DOM أو أسرار؛ تحقق الخادم ملزم |
| `packages/ui/` | التوكنز ومكونات React والسلوك القابل للمشاركة |
| `packages/client/` | API client وحالة الرحلات وواجهات platform adapters، دون اعتماد خادمي |
| `apps/mobile/` | غلاف العميل وCapacitor وAndroid؛ ينشأ كتجربة في M0 |
| `supabase/migrations/`, `supabase/seed.sql` | مخطط وصلاحيات قابلة لإعادة الإنشاء وبيانات اختبار غير شخصية |
| `tests/integration/`, `tests/e2e/`, `tests/load/` | التحقق من العقود والرحلات والتزامن والحمل |
| `docs/evidence/` | نتيجة كل مرحلة، أوامر التحقق، ظروف التشغيل والقيود الفعلية |

هذه حدود داخل مستودع واحد، وليست microservices. لا مشروع أو أسرار أو OAuth خاص بكنف. لا إنشاء طبقات شكلية لمجرد ملء هذا الجدول.

## تسلسل الاعتماد

```text
B0 → B1 → B2 → B3 → B4 → B5 → B6 → B7
                                         ↓
                  تجربة شاملة → تقرير كامل → إصلاح → مراجعة نهائية
```

لا يبدأ تنفيذ المرحلة التالية قبل إغلاق بوابة الحالية. يمكن توزيع أعمال مستقلة داخل المرحلة نفسها على عوامل متوازية، مع دمج ومراجعة واحدة. تغييرات schema والمعاملات المشتركة تُدمج تسلسليًا. M0/M1/M2 مؤجلة بطلب المستخدم.

## B0 — تجهيز المشروع وإثبات المسار التقني

**يعتمد على:** الوثائق والأصول الحالية.

- حصر ملفات الهوية والخطوط والتوكنز والمكونات، نسخ المطلوب فقط مع تراخيصه وبصماته؛ الحفاظ على اللاندنج والشعار المقبولين.
- تثبيت package manager وlockfile والإصدارات، وإعداد TypeScript/lint/build وعينة اختبار، و`.env.example` بلا أسرار. اختيار مكتبات مصانة مناسبة قبل بناء بدائل خاصة.
- إعداد build متوافق مع Workers؛ اختبار واجهة + API صغير + قراءة/كتابة معزولة ومصادقة تجريبية، وتسجيل التوافق والـCPU. التطبيق المصغر نفسه قابل لإعادة التشغيل.
- حسم طريقة استخراج/مشاركة عميل React للموبايل دون الاعتماد على SSR داخل APK. إعداد عقد cookies/token وredirects وCORS والتخزين دون تسريب صلاحيات.
- رسم حالات أول رحلة: تحميل/فارغ/فشل/حفظ/تعارض/انقطاع، وهندسة shell للهاتف والكمبيوتر. تحديد عقود API والمخطط الأول فقط، ثم توسيعه مع المراحل.
- إعداد local Supabase أو بيئة تطوير معزولة حسب إمكانات الجهاز؛ التغييرات migrations وليست نقرات غير موثقة.

**ملفات:** إعدادات الجذر و`apps/web/` و`packages/*` و`supabase/`؛ وثيقة قرار التوافق في `docs/evidence/B0.md`.

**بوابة:** تثبيت وتشغيل من تعليمات واضحة، نجاح build/runtime المعتمد وطلب API وحفظ/قراءة اختبارية، عدم وجود أسرار في bundle/Git؛ نتيجة CPU وتوافق العميل موثقة. قبل النشر العام يلزم تحقق على Workers الفعلي، لا محاكاة فقط.

**حد الخدمات:** إعداد مشاريع Supabase/Cloudflare ونسخة معاينة بعيدة عند تفويض يغطيها؛ إلى ذلك الحين يمكن استكمال الإعداد المحلي. لا تغيير DNS أو شراء خطة في هذه المرحلة لمجرد وجود حساب مفتوح.

## B1 — الحسابات والصلاحيات وأساس تجربة الاستخدام

**يعتمد على:** B0. **ملفات:** accounts/auth في web/server، contracts/client/ui، migrations، اختبارات ملكية ودخول.

- Google OAuth وEmail OTP بالإعداد المناسب؛ الاسم والمنطقة الزمنية والنية Learning/Work، مع عودة الوجهة الأصلية بعد الدخول.
- الجداول الأساسية وRLS والأدوار؛ فصل ملف العرض العام عن بيانات المالك. عدم منح الدور من metadata يحررها المستخدم.
- shell والتنقل المعتمد، Settings الأساسية، loading/empty/error/save states، ومراقبة أخطاء بلا محتوى خاص.
- التعامل مع انتهاء الجلسة والخروج وتبديل الحساب وطابور محلي إن وُجد؛ واجهة Work-only لا تفترض وجود كورس.
- ربط أزرار اللاندنج بالتسجيل والمكتبة؛ لا إعادة تصميم غير لازمة. اختبار callbacks والروابط على بيئة التطوير المعتمدة.

**بوابة:** أجزاء المصادقة والعودة للوجهة المتاحة من AC01، وعزل الحسابات AC03 وصلاحيات السجلات المتاحة AC04، على المتصفح نفسه ومن جهازين. الرجوع لروم مستقبلية يختبر كوجهة محفوظة فقط؛ تجربة الروم الفعلية في B5. AC02 يبدأ كاختيار Work-only دون كورس هنا، ويكتمل ببدء جلسة فعلية في B4. لا ادعاء باختبار تصدير أو إشعارات أو طابور لم يُبنَ؛ يُعاد AC03/AC04 مع إضافتها في B4/B6/B7. البريد العام يحتاج مزود إرسال إنتاجي مثبت قبل B7.

## B2 — أول رحلة تعلم كاملة

**يعتمد على:** B1. **ملفات:** catalog/planning/progress، API contracts، migrations، Library/My Courses/Course/Plan/Today، fixtures للكورسين.

- تدقيق Google PM وCS50 Business وترتيب أنشطتهما ومصادرهما؛ الروابط والتقديرات معلنة، ولا نسخ فيديوهات أو ادعاء مزامنة رسمية.
- مكتبة وتفاصيل منهج، إضافة كورس خاص وتحرير مسودة Course/Module/Task، وانضمام بنسخة ونطاق ثابتين وتقدم سابق منفصل.
- محرك خطة أولى حتمي: availability واحدة لجميع الكورسات، تاريخ هدف، أيام راحة، احتياطي، ترتيب ومتطلبات سابقة، عجز واضح.
- Preview ثم Apply، Today بخطوة تالية واضحة، فتح المصدر، Complete/Undo وحفظ من الخادم. بنية أحداث التقدم تدعم الجزئي لاحقًا دون احتساب وقت من الإكمال.
- My Courses وMy Plan يعرضان الواقع نفسه؛ إعادة فتح وجهاز ثانٍ لا يفقدان الإنجاز. تقارير التقدم الأساسية تتسع في B6.

**بوابة:** الرحلة المفيدة كاملة + AC01 لوجهة الكورس وAC06–AC07؛ كورس ثانٍ لا يضاعف السعة؛ retry لا يكرر الإنجاز. السابق لا يولد نقاط أسبوع جديد. اختبار كيبورد وهاتف وحفظ فاشل يحتفظ بالمدخلات.

## M0 — تجربة APK مبكرة (مؤجلة، خارج النطاق الحالي)

**يعتمد على:** B2. **ملفات:** `apps/mobile/` وadapters في client، تعليمات build و`docs/evidence/M0.md`.

- تغليف رحلة B2 بعميل قابل للبناء، وتثبيت APK اختبار محليًا دون نشر متجر.
- تسجيل الدخول وروابط العودة والكورسات والإنجاز؛ نفس API والحساب، مع التحقق من التخزين والرجوع والروابط الخارجية.
- قياس ما أُعيد استخدامه فعليًا وما يحتاج فصلًا عن Next، وتعديل حدود الحزم قبل تضخم عدد الشاشات.

**بوابة:** AND01–AND03 وAND08 على هاتف Android فعلي؛ إن لم يتوفر هاتف تُسجل نتيجة المحاكي وحدها والبوابة غير مكتملة. هذا APK جدوى محدود، لا تطبيق كامل أو جاهز للتوزيع العام.

## B3 — الاستدراك والعمل الجزئي

**يعتمد على:** B2؛ لا بوابة هاتف في النطاق الحالي. **ملفات:** domain/planner، planning/progress APIs، Recovery/Plan/Today ومخطط العمل الجزئي.

- Worked on وremaining estimate، Unknown effort، pins وأولويات الكورسات والاستثناءات والراحة وإيقاف الخطة.
- العودة بعد يوم أو يومين أو انقطاع طويل؛ Before/After وتفسير أثر الموعد والسعة والتقدير، ثم Apply صريح.
- كشف المتبقي غير الموزع، اعتماد الجزء الممكن بإقرار، تعديل الموعد/السعة باختيار؛ لا Fits زائفة.
- رفض preview قديمة عند تغير التقدم، وUndo للاستدراك كاقتراح جديد يحفظ الإنجاز الحديث.

**بوابة:** RC01–RC13 بما فيها DST/منتصف الليل والسعة المشتركة؛ لا إسقاط مهام ولا حذف ماضٍ ولا خصم جهد مرتين. حركة المقارنة تشرح التغيير وتحترم reduced motion.

## B4 — سجل الوقت والتركيز الفردي

**يعتمد على:** B3. **ملفات:** time module ومعاملاته وقيوده، Focus/Activity، client session state، outbox/jobs.

- سجل TimeSession/Interval/Correction واحد؛ Solo Pomodoro وOpen وWork، pause/resume/finish/review والتحكم عبر الأجهزة.
- ساعة الخادم وحدود الجولة والسقف؛ Finalized عند نهاية المحدد وNeedsReview عند سقف المفتوح. لا بدء رصيد الجولة التالية تلقائيًا.
- استراحة منفصلة؛ ملخص الجلسة يسأل عن نتيجة النشاط دون إكماله تلقائيًا. اليدوي شخصي خارج ترتيب المنافسة.
- retry وidempotency وOffline Stop وتصحيح الفترة، والتعامل مع تبويبين وفقد الرد وانتهاء التحكم.
- dispatcher محمي وعمليات قصيرة قابلة للإعادة؛ job متأخر لا يغير حد الوقت الأصلي. مراقبة أخطاء الأوامر والحصة.

**بوابة:** AC02 ببدء جلسة Work فعلية وTM01–TM07 وOP01، وإعادة AC03/AC04 بعد إضافة المزامنة وسجل الوقت؛ جلسة واحدة للحساب حتى مع بدء متزامن، لا وقت مكرر أو وقت استراحة. فصل effort التخطيط عن timer في الاختبارات.

## M1 — اختبار Android للوقت والخلفية (مؤجل، خارج النطاق الحالي)

**يعتمد على:** B4 وM0. **ملفات:** mobile lifecycle/notification adapters و`docs/evidence/M1.md`.

- تجربة شاشة مقفلة، سكون، force-stop وإعادة فتح، إذن تنبيه مرفوض/مسحوب، تغيير الساعة، وفقد الشبكة.
- استعادة snapshot وتحكم جهاز آخر وإلغاء التنبيه المحلي عند الإنهاء؛ توثيق قيود التحديث بين الأجهزة في الخلفية.
- اختيار أبسط تكامل مدعوم للتنبيه، دون خدمة دائمة تستهلك البطارية لمجرد تشغيل عدّاد كل ثانية.

**بوابة:** AND04–AND06؛ الرصيد صحيح مستقلًا عن وصول التنبيه. تقرير هاتف فعلي يصف السلوك والقيود؛ المحاكي أو مجرد إصدار APK لا يثبت نجاح الخلفية.

## B5 — الغرف العامة والبومودورو الجماعي

**يعتمد على:** B4؛ التحقق الحالي من توقيت الويب. **ملفات:** rooms على نفس time ledger، directory/lobby/room UI، Realtime وmoderation الأساسية، tests/load.

- قائمة غرف وفلترة/إنشاء لروم موضوع أو كورس عام، lobby، preset، Run محدود وجولات، انضمام متأخر وخيار انتظار.
- ساعة مشتركة مستقلة عن وقت كل فرد؛ الانضمام للجولة صريح؛ pause شخصي لا يوقف الآخرين، ومغادرة المضيف لا توقف الجولة.
- presence lease وreconnect ونقل المضيف والمقعد الأخير والانتهاء، ومنع تضارب الروم مع الفردي والنقل الذري بينهما.
- الإزالة والحظر والإبلاغ والإيقاف وصلاحيات snapshot لكل مشاهد؛ بث phase/version/count فقط.
- اختبار الحمل الموثق في Rooms: أربع غرف ×20 عضوًا +20 اتصالًا ثانويًا، وظروف الشبكة والـCPU والرسائل والحصة الشهرية؛ الأرقام هدف اختبار لا قدرة مثبتة.

**بوابة:** AC01 لوجهة الروم الفعلية وRF01–RF22 والاختبارات المشتركة للوقت/الخصوصية؛ ثم حمل بسعة معلنة. الغرف جزء من النسخة الكاملة المطلوبة، لا تؤجل إلى ما بعد beta.

## B6 — التقدم والمجتمع والمحتوى والإدارة

**يعتمد على:** B5؛ تصميم الشاشات يمكن تحضيره قبلها. **ملفات:** social/ranking/catalog review/operations، Progress/Circle/People/Boards/Contributions/Admin/Settings.

- Progress يفصل المنهج والوقت والإيقاع وتوقع الخطة؛ Activity يتتبع المصدر والتصحيح.
- follow request وقبول ومنح حقول ومشاهدة مسبقة وسحب الإذن؛ الإكمال لا ينشر milestone تلقائيًا. حظر يحترم cache/socket.
- ترتيب ساعات عام اختياري بفلاتر Work/Learning وترتيب كورس ضمن version/scope متجانسين؛ baseline واليدوي خارج credit الجديد.
- snapshot طلب نشر، مراجعة وسبب قرار، وإصدارات ثابتة وترقية اختيارية بمعاينة؛ صلاحيات المراجع لا تكشف تقدم صاحب المنهج الخاص.
- إكمال notifications والتفضيلات وأدوات التشغيل والإبلاغ، jobs موثوقة، export/delete والروابط الخاصة قصيرة العمر؛ لا اعتدال صوري بلا مسؤول.

**بوابة:** AC05 وSC01–SC05 وLB01–LB04 وCM01–CM02 وOP03، وتجربة تصدير/حذف أولية وإعادة AC03/AC04 على الإشعارات والتصدير. انسحاب المستخدم يخفي بياناته دون انتظار projection؛ لا تكشف أسماء كورس خاص أو ملاحظاته.

## B7 — التحقق والإطلاق التجريبي للويب

**يعتمد على:** B0–B6. تحقق الويب فقط؛ الهاتف مؤجل صراحة.

- اختبار الرحلات الأساسية مع خمسة أشخاص كبداية: خطة أولى، كورس ثانٍ، عودة بعد يومين، روم متأخرة، خصوصية، Work-only؛ تسجيل العوائق لا الاكتفاء بالرأي الجمالي.
- responsive وكيبورد وتباين وتكبير وreduced motion؛ تحقق أداء الأجهزة والشبكات، ثم قياسات فعلية بعد وجود مستخدمين. أهداف Delivery ليست نتائج مسبقة.
- مراجعة RLS/IDOR والأدوار والـAPI وتحديثات الخصوصية؛ restore drill مع tombstones كي لا يعيد حسابًا محذوفًا، وOP02 وبقية اختبارات التشغيل.
- إعداد النسخ الخارجية والرصد والحدود والفشل والرجوع لإصدار سابق؛ تشغيل مراقب على الخطط المجانية دون upgrade تلقائي.
- عند تفويض التنفيذ الخارجي: إعداد/مراجعة Cloudflare DNS والدومين وTLS وسجلات البريد الموجودة، SMTP وOAuth callbacks، سياسة الخدمة والخصوصية ومسؤول المراجعة.
- alpha محدودة يمكن أن تسبق اكتمال كل الميزات بتسمية دقيقة؛ beta الكاملة بعد P0. فتح التسجيل العام والنشر أعمال منفصلة عن تسجيل هذه الخطة.

**بوابة:** مصفوفة D01–D15 بلا فجوات مانعة، أدلة UX/أمان/حمل/استعادة، لا فقد محفوظ أو تسريب أو تضاعف وقت قابل للتكرار؛ قيود معلنة ومسؤول تشغيل. لا تاريخ تسليم ثابت قبل معايرة الجهد بعد B0.

## M2 — إصدار Android الكامل (مؤجل، خارج النطاق الحالي)

**يعتمد على:** B7 + نجاح M0/M1 أو معالجة قصورهما؛ جاهزية النسخة والنشر يُسجلان منفصلين.

- نقل الرحلات المكتملة للحاوية وتكييف التنقل والإشعارات والروابط والتخزين وتجربة الانقطاع، مع اختبار الغرف في الخلفية بنفس عقود الحضور.
- AND01–AND09، خاصة انتهاء lease والتبديل بين الأجهزة، وأداء هاتف متوسط والتحديث من نسخة قديمة.
- توقيع وحماية المفتاح، package ID ثابت بعد التحقق، الأيقونات وsplash، سياسة تحديث وتوافق API، APK تجريبي ومخرجات المتجر عند طلبه.
- مراجعة متطلبات التوزيع والخصوصية والأذونات وقت التنفيذ. حساب متجر ورسومه أو نشره ليس ضمن تفويض التسجيل الحالي.

**بوابة:** رحلة Android الكاملة على أجهزة فعلية موثقة + build قابل للتكرار وتحديث يحفظ البيانات؛ لا وعد بتنبيه يصل في كل ظروف النظام. إطلاق المتجر يحتاج تفويضًا يغطيه.
