# B1 — عقد الحساب والمصادقة المنفذ

المرجع هنا هو الكود الحالي، لا بقية مواصفات المنصة المستقبلية. نتائج التشغيل وحدود الإثبات الحي في [تقرير B1](evidence/B1.md)؛ لا تكرر هذه الوثيقة أعداد الاختبارات. دليل B0 السابق يصف تجربته المؤقتة ولا يحكم جلسات B1.

## مسارات HTTP

كل المسارات التالية تحت `/api/v1` عدا callback. استجابات الحساب خاصة: `Cache-Control: private, no-store` و`Vary: Origin, Cookie`. أخطاء JSON بصيغة `{error:{code}}`، دون تفاصيل قاعدة البيانات أو مفاتيح أو رموز جلسة.

| المسار | المدخل | النتيجة |
|---|---|---|
| `GET /auth/session` | جلسة cookie أو Bearer صالح | `data.user={id,email}` أو `null`، و`data.providers={email,google}`؛ علم المزوّد ليس إثبات نجاح دخوله |
| `POST /auth/otp` | `{email,next?}` | `data.sent=true` بعد قبول Auth؛ لا يدّعي وصول الرسالة إلى صندوق خارجي |
| `POST /auth/verify` | `{email,token,next?}` | تحقق كود البريد، حفظ الجلسة في cookies، ثم `data.next` داخلي منقح؛ لا tokens في JSON |
| `POST /auth/google` | `{next?}` | `data.url` من Supabase لبدء OAuth/PKCE؛ يتطلب تفعيل Google في البيئة |
| `GET /auth/callback` | `code` من تدفق PKCE | تبادل الكود ثم `303` إلى المقصد المحفوظ؛ الإلغاء/الفشل إلى `/auth?error=callback_failed&next=...` |
| `POST /auth/logout` | `{}` | حذف cookies الخاصة بالمصادقة والعودة، و`data={signedOut:true,serverRevoked:boolean}` عند رجوع SDK؛ `serverRevoked=false` لا يثبت سحب الجلسة لدى المزوّد |
| `GET /me` | هوية متحققة | `data={accountId,profile,role}`؛ `profile=null` قبل أول حفظ |
| `PATCH /me` | أمر الحفظ أدناه | نفس `data` مع `revision,operationId,serverTime,requestId`؛ النجاح بعد commit |
| `OPTIONS /me` | Origin مدرج | preflight محدد للأفعال والترويسات؛ ليس تصريحًا بقراءة بيانات دون هوية |

طلبات التعديل JSON بحد فعلي قدره 4096 بايت، بما يشمل الجسم المتدفق. البريد يُقلم ويحوّل إلى أحرف صغيرة؛ الكود يقبل أرقامًا بطول 6–10، وإعداد Auth المحلي يصدر 6 أرقام. الحقول الزائدة مرفوضة. `next` يقتصر على مسارات المنتج الداخلية المعتمدة، يحتفظ بالاستعلام والجزء الداخلي، ويرفض الروابط الخارجية ومحاولات الالتفاف؛ البديل `/app/today`. الرجوع إلى رابط روم محفوظ لا يعني تنفيذ الروم أو الانضمام إليها.

## الجلسة والحدود بين الويب والموبايل

الويب يستخدم `@supabase/ssr` على الخادم فقط. هوية كل طلب خاص تتحقق عبر `getUser()`، وتُنقل تغييرات cookies الناتجة عن SDK إلى الرد. cookies هي `HttpOnly; SameSite=Lax; Path=/`؛ مع HTTPS تصبح `Secure` وبادئة `__Host-`. HTTP مسموح للتطوير المحلي فقط. المتصفح لا يستلم access/refresh tokens في JSON أو يخزنها في localStorage، ولا يوجد اعتماد على بيانات مستخدم مرسلة من الواجهة للتفويض. هذه آلية التطبيق المنفذة؛ يدير SDK أساس cookies وPKCE وفق [دليل Supabase SSR](https://supabase.com/docs/guides/auth/server-side/advanced-guide).

مسار Bearer لقراءة/تعديل الحساب يختار اعتماد الترويسة صراحة؛ لا يعود إلى cookies إن كانت الترويسة غير صالحة. هذا يتيح استخدام API من عميل منفصل، لكنه **ليس تنفيذ مصادقة Android أو تخزينه الآمن أو روابط عودته**؛ تلك بوابات M0/M1. مسارات بدء/تحقق الدخول والخروج الحالية خاصة بويب same-origin، ولا تقبل Bearer بدل cookies.

## CSRF وتبديل الحساب

- تعديل بجلسة cookie يتطلب `Origin` مطابقًا لـ`DIMA_APP_ORIGIN` الموثوق، ولا يؤخذ origin من Host غير موثوق. Bearer يسمح بغياب Origin؛ إن وُجد فيجب أن يكون مدرجًا. CORS صريح دون `*` أو السماح العام بـcredentials.
- `PATCH /me` بجلسة cookie يتطلب `X-Dima-Account-Id` مساويًا لهوية الخادم. الترويسة اختيارية مع Bearer، لكنها تُفحص متى وُجدت. عدم التطابق يرجع `409 ACCOUNT_CHANGED` بدل حفظ مسودة A في حساب B.
- الواجهة تقارن `data.accountId` بهوية الجلسة قبل العرض، وتستبعد الاستجابات القديمة عند تغير الحساب. لا تكتفي بفحص هوية سابق للحفظ.
- الخروج يقفل العرض الخاص ويمسح حالته فورًا، ويبلغ التبويبات عبر `BroadcastChannel`. يحفظ علامة غير شخصية `dima-signout-pending` حتى إتمام طلب الخروج؛ عند انقطاع الشبكة يبقى العرض مقفولًا مع Retry وتحذير أن جلسة الخادم قد تكون قائمة. العلامة ليست token ولا إثبات إلغاء الجلسة، وإذا منع المتصفح localStorage يبقى البديل في ذاكرة الصفحة فقط.

## أمر الحساب والصلاحيات

صيغة `PATCH /me` الفعلية مسطحة في B1، وليست داخل مفتاح `payload`:

```json
{
  "displayName": "Member",
  "timezone": "Africa/Cairo",
  "intent": "work",
  "appearance": "system",
  "reducedMotion": false,
  "onboarded": true,
  "expectedRevision": 0,
  "operationId": "75b05345-c269-4736-b759-567078d84663"
}
```

الاسم مقلم حتى 80 حرفًا وبلا محارف تحكم؛ يمكن تركه فارغًا لمسودة `onboarded=false` فقط. المنطقة الزمنية `UTC` أو اسم IANA صالح يراجعه التطبيق وقاعدة البيانات. النية `learning|work`، والمظهر `system|light|dark`. بدء الاستخدام بالعمل لا يحتاج كورسًا. بعد إكمال onboarding لا يعيده حفظ مسودة إلى حالة غير مكتملة.

الملكية من `auth.uid()` داخل دالة الحفظ، لا من المدخل. `account_profiles` و`profile_operations` خاصان بالمالك عبر RLS. `account_roles` جدول منح محمي؛ الدور الافتراضي `member`، ولا تمنح Auth user metadata أو حقول الملف دور `moderator/admin`. القراءة تستخدم صلاحيات المستخدم، دون service-role في API.

`public_profiles` إسقاط منفصل خالٍ من البريد والمنطقة الزمنية والتفضيلات والأدوار والنشاط؛ الظهور افتراضيًا مغلق. لا يوجد أمر نشر عام في B1، وحفظ الملف الخاص لا ينشئ إعلانًا عامًا. الكتابة المباشرة من العميل على جداول الملف/العمليات/الأدوار/الإسقاط العام ممنوعة؛ الحفظ عبر RPC محدد فقط، مع `SECURITY DEFINER` و`search_path` فارغ وأسماء جداول مؤهلة.

الحفظ يقفل حساب المستخدم داخل معاملة واحدة. أول حفظ يتطلب revision صفرًا؛ كل حفظ جديد ناجح يزيده مرة. اختلاف `expectedRevision` يرجع `REVISION_CONFLICT`. تكرار `(account,operationId)` بنفس الأمر يعيد نتيجة العملية الأصلية دون زيادة؛ تغيّر محتواها يرجع `IDEMPOTENCY_MISMATCH`. الواجهة تعيد نفس operationId عند إعادة نفس الحفظ بعد فقد الرد، وتتيح مراجعة النسخة الأحدث عند التعارض دون إسقاط المسودة خفية. لا يُستنتج من هذا تنفيذ طابور offline أو أوامر الكورسات والوقت المستقبلية.

## الفشل وحدود التشغيل

الردود المتحكم بها تشمل `400 INVALID_JSON`، `401 AUTH_REQUIRED / CODE_INVALID_OR_EXPIRED`، `403 ORIGIN_NOT_ALLOWED`، تعارضات `409` السابقة، `413 BODY_TOO_LARGE`، `415 JSON_REQUIRED`، `422 INVALID_INPUT`، `429 RATE_LIMITED`، و`503` لتعطل الخدمة أو غياب الإعداد. فقد Auth المؤقت لا يُعرض باعتباره نجاحًا؛ أخطاء SDK/DB غير المعروفة تصبح خطأ خدمة آمنًا. هذا لا يثبت تشغيل مراقبة أخطاء بعيدة.

البريد المحلي يمر عبر Auth وSMTP إلى Mailpit، مع autoconfirm معطل وقالب OTP يخدمه HTTP داخلي. هذا يتبع طريقة [قوالب البريد في Supabase المستضاف ذاتيًا](https://supabase.com/docs/guides/self-hosting/custom-email-templates)، ولا يثبت توصيل بريد إنتاجي أو اعتماد دومين إرسال. إعداد Google الخارجي وحفظه الخاص لا يكفيان وحدهما لإثبات رحلة الدخول؛ نتيجة التجربة الحية مرجعها تقرير B1. لا توجد أسرار Google أو رموز اختبار في هذه الوثيقة.

الكورسات والخطط والجلسات والغرف والنشر الاجتماعي وتصدير/حذف الحساب وظائف مراحل لاحقة. API الحالي لا يزعم تنفيذها أو استيفاء اختبارات صلاحياتها قبل بنائها.
