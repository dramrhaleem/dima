## ترحيل عرض النسبة الشخصية في B6

**فحص المصدر الحالي، تصميم غير منفذ:** `packages/ui/src/learning.tsx` يحسب `progress()` بعدد Required المكتمل/الإجمالي، و`Progress` يستخدم العدد نفسه للنسبة وشريط التقدم في My Courses وتفاصيل الكورس. هذا يختلف عن النسبة الموزونة الملزمة في §6 من [قواعد التقدم](RECOVERY_AND_PROGRESS_SPEC_AR.md). تستبدل B6 هذا الحساب في جميع مواضعه، ومنها Overview الجديدة، بدالة domain واحدة تعيد أوزان المكتمل/المقام والنسبة وحالة التصنيف، مع إبقاء أعداد الأنشطة وprior/new منفصلة. الوزن حسب سياسة v1 لا estimated minutes؛ مثال Reading + Project وإكمال Reading فقط = وزن 1 من 9، وليس 50% رغم إكمال نشاط من اثنين. المقام الشخصي هو Required داخل اختيار المتعلم؛ ComparisonScope العام له مقام مستقل ثابت ولا يستبدل أحدهما الآخر.

محرر المسودة الحالي يتيح `reading`, `video`, `quiz`, `assignment`, `project` فقط، وهي الأنواع الخمسة المصنفة؛ لكن عقد `LearningTask.kind` يقبل نصًا أوسع، فيمكن أن تحتوي بيانات خاصة محفوظة على نوع آخر. لا نضيّق العقد بما يكسر الكورس الموجود ولا نخمن وزنًا: تبقى أعداد الإكمال والتقدم المحفوظ قابلين للعرض والاستعمال، وتصبح النسبة الموزونة `null` مع سبب `Classification needed` إذا وُجد Required غير مصنف؛ هذه حالة مختلفة عن صفر المقام. المحرر يعرض النوع القديم بوضوح كقيمة غير مصنفة ويطلب اختيارًا صريحًا عند التصنيف، ولا يحوله تلقائيًا إلى أول خيار. تعديل draft لا يغيّر snapshot التسجيل أو تاريخ الإنجاز بصمت؛ أي تحديث لنوع داخل النسخة المثبتة يمر بمعاينة/ترقية معتمدة. اعتماد public scoring يمنع Required غير المربوط بسياسة أوزان. Optional/Supporting تبقى خارج المقام.

## إعادة التحقق للعمليات الحساسة — مقترح تنفيذ محدود

**1 نوفمبر 2026: تصميم فقط، لا يبدأ قبل إغلاق B5.** الاختيار المقترح للحذف هو رابط بريد `PKCE` مخصص إلى البريد المؤكد للحساب القائم، مع تحدٍّ مرتبط بالحساب والجلسة التي بدأت الطلب. يعاد استخدام هذا الحاجز عند الحاجة في أوامر التصدير الحساسة، مع purpose مستقلة؛ لا يغيّر ذلك عقد ملف التصدير والتنزيل أو بروتوكول [Prepare → acknowledgment → Apply](PRIVACY_LEDGER_CONTRACT_AR.md). يثبت المسار حيازة حديثة للرابط المرسل إلى البريد، وليس إدخال كلمة مرور Google أو تحققًا متعدد العوامل. لا يُقبل اختيار حساب Google أو `amr=oauth` أو `iat` من refresh أو وقت دخول عام للحساب كإثبات بديل.

1. **بدء التحدي:** طلب same-origin يتحقق من Auth و`X-Dima-Account-Id`؛ البريد من Auth لا من جسم الطلب. سجل خادمي خاص يربط UUID/جيل الحساب و`session_id` الأصلية وpurpose و`operationId` وhash المحتوى المقصود ووقت الإنشاء/الانتهاء وحالة الاستهلاك وhash سر المتصفح. اقتراح المدة عشر دقائق، مع تحدٍّ نشط واحد لهذا الغرض وحدود إرسال. عميل Auth مستقل يستخدم `flowType: 'pkce'` و`shouldCreateUser: false`، ويحتفظ بالـverifier في تخزين خادمي خاص بالتحدي، منفصل عن مخزن جلسة الدخول.
2. **الرابط وتجربة المستخدم:** الرسالة تطلب فتح الرابط في **المتصفح وملف المستخدم نفسيهما** اللذين بدآ العملية. يستخدم الرابط مسار Auth الأصلي للتحقق ثم callback مخصصة ومسموحًا بها؛ لا token في `next` أو وجهة خارجية. غياب سر المتصفح أو الجلسة الأصلية، أو تبديل الحساب، يعرض إعادة بدء التحقق دون تنفيذ العملية أو تبديل الحساب تلقائيًا. callback لا تحذف الحساب؛ تعود إلى تأكيد الإجراء الصريح. قالب البريد الحالي يعرض OTP فقط؛ دمج الرابط والمحافظة على الدخول القائم يحتاجان تنفيذًا واختبارًا لاحقين، وليس المسار عاملًا حاليًا.
3. **فحص الإثبات:** الخادم وحده يبادل code باستخدام verifier الخاصة بالتحدي، ثم يتحقق من توقيع JWT وissuer/audience وexpiry و`sub` المطابقة للحساب، ومن `amr.method = magiclink` المتوقع لهذا المسار. timestamp يجب أن تكون عدد ثوانٍ صحيحة؛ تقارن بـ`floor(challengeStartedAtMs / 1000)` و`floor(serverNowMs / 1000)` وحد freshness بالثواني، ولا تقارن مباشرة بزمن milliseconds أو تشترط دقة أجزاء الثانية غير الموجودة. مساواة ثانية بدء التحدي مسموحة؛ ربط code/verifier، وليس التوقيت وحده، يمنع تقديم إثبات سابق أو من جهاز آخر. غياب AMR أو اختلافها يفشل مغلقًا حتى يُراجع الدليل الفعلي. **لا يقبل endpoint JWT يقدمها العميل بوصفها إثبات إعادة تحقق.**
4. **العزل والاستهلاك:** بعد التحقق تسجل منحة خادمية لخمس دقائق كحد أقصى، ولا تتجاوز انتهاء التحدي؛ تربط بالجلسة الأصلية وpurpose وpayload. تُهمل رموز جلسة الإثبات المؤقتة وتُلغى تلك الجلسة فقط بـlocal scope، دون كتابة cookies الجلسة العادية أو استبدالها. تُفحص الجلسة الأصلية مجددًا عند تنفيذ الإجراء، وتستهلك المنحة ذريًا مع Prepare للحذف أو أمر التصدير المحدد. إعادة نفس `operationId` تعيد receipt القائمة؛ لا تسمح بإجراء آخر أو payload مختلفة. تُبطل واجهة التحدي عند logout/تغير الحساب، ولا يستطيع callback أو رد متأخر إحياء حالة الحساب السابق. فقد رد مبادلة code قبل تسجيل الإثبات يستلزم تحديًا جديدًا؛ لا تخمين نجاحه.

**حدود الاعتماد:** `signInWithOtp` لا يجعل إدخال الكود عبر `verifyOtp` مرتبطًا بـPKCE تلقائيًا؛ النسخة المثبتة `auth-js@2.118.0` ترسل POST `/verify` دون verifier، وAuth المثبتة في compose، `v2.197.0`، تصدر في هذا المسار جلسة `otp` مباشرة. المسار المختار هو native magic-link GET verification ثم code exchange؛ لا يُستبدل بـ`verifyOtp(token_hash)` مع ادعاء الضمان نفسه. كذلك `reauthenticate()` ترسل nonce لتحديث كلمة المرور عبر `updateUser()`؛ ليست لدينا API مثبتة للتحقق العام من nonce للحذف.

**بوابة الإثبات بعد B5:** تجربة محلية على Auth المثبتة تثبت AMR وتوقيت الثواني وربط verifier، ورفض refresh وحده وحساب/جلسة/متصفح آخر وcode معادة أو منتهية، واستهلاكًا متزامنًا وتبديل الحساب أثناء callback وفقد الرد. يجب اختبار سياسة الجلسات وAAL الفعلية: إنشاء جلسة إثبات قد يتعارض مع single-session policy أو متطلبات AAL2؛ لا تخفيض صامت للـassurance ولا وعد بدعم سياسة لم يثبت توافقها. يُرفض المسار غير المتوافق حتى يُحسم تصميمه. SMTP المستضافة، البريد المؤكد لحساب Google القائم، القالب والredirects، تسليم الرسائل، prefetch الروابط وسياسة الجلسات المستضافة بوابات مستقلة؛ Mailpit وكلمات مرور الحسابات الاصطناعية لا تغلقها. لم يحدث إرسال بريد أو اختبار DB أو تغيير runtime لهذا المقترح.

المراجع الأولية: [Supabase PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow)، [JWT/AMR](https://supabase.com/docs/guides/auth/jwt-fields)، [مصدر verification المثبت](https://github.com/supabase/auth/blob/v2.197.0/internal/api/verify.go)، [مصدر PKCE exchange المثبت](https://github.com/supabase/auth/blob/v2.197.0/internal/api/token.go)، [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect)، [OIDC freshness](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)، [SMTP](https://supabase.com/docs/guides/auth/auth-smtp). مواضع الدمج بعد الإذن ببدء المرحلة: `apps/web/src/server/auth.ts` لعزل proof context والتحقق من claims، `apps/web/src/server/account.ts` لفحص المالك، و`packages/ui/src/account.tsx` لأسوار تغير الحساب؛ لا تنفيذ في هذه المراجعة.

## ترتيب البناء داخل المرحلة

1. تثبيت العقود والملكية وDTOs، ثم مخطط البيانات والأقفال والأهلية وlineage. اختبار نوافذ UTC والتعادل والمقام الصفري وUndo/Recomplete والتصحيح قبل واجهة الترتيب.
2. Progress بأربعة معانٍ منفصلة: المنهج والوقت والإيقاع وصحة الخطة. إعادة استخدام Activity وتفاصيل الجلسة، مع فلاتر وتصفح محدود للبيانات المتراكمة.
3. Circle وPeople والموافقة الاتجاهية والمنح المحددة ومعاينة الجمهور والسحب والحظر. قبول المتابعة دون حقول لا يمنح مقاييس. المعلم يحتاج نشرًا صريحًا ومصدرًا صالحًا ومنحة مستقلة.
4. لوحات اختيارية، ومعاينة ما سيصبح عامًا قبل الانضمام. الترتيب الأسبوعي للكورس مختلف عن الإجمالي، ومجموعات المقارنة ثابتة النسخة والنطاق. تحديث الصفوف باختيار المستخدم، مع وقت الحساب وبيان التصحيح.
5. طلب نشر snapshot ثابت، مراجعة بسبب مسجل، إصدار ثابت، وترقية اختيارية بمعاينة added/removed/mapped/unresolved وتغير المقام. اعتماد مساهمة لا ينشئ انضمامًا مكررًا أو استحقاقًا ثانيًا.
6. إشعارات داخلية وتفضيلات، ثم الإدارة والتصدير والحذف ووظائف التشغيل. فتح الرابط يعيد فحص الوصول؛ نص الإشعار لا يحتفظ بعنوان خاص بعد سحب مصدره. لا بريد أو push تحفيزي مفترض التشغيل.
7. اختبار الوظائف والعزل والسباقات، ثم رحلة متصفح كاملة ومراجعة مستقلة وتصحيح وتحقق قبل إغلاق B6.

## نقاط مراجعة لا يجوز تجاوزها

- **الخصوصية:** APIs تفحص الإذن الحالي قبل الإرجاع، حتى لو كانت الإسقاطات قديمة. تنظيف كاش العميل وإشارات الإبطال لا يحلان محل ذلك. أي قناة realtime جديدة تتطلب عقدًا وحدودًا محسوبة؛ لا مضاعفة sockets أو صلاحيات الرموز دون اختبار. لا وعد بمحو ما سبق أن شاهده الآخرون.
- **النشر:** المراجع يستلم المنهج فقط؛ لا خطة أو تقدم أو ملاحظات. الحقوق والمصدر وscope وسياسة النقاط جزء من قرار المراجعة. الانسحاب من الظهور لا يمسح سجل صاحبه.
- **الحذف:** هجرة B5 `028000` ربطت مالك الغرفة والعضوية بالبروفايل. لا يكفي استدعاء حذف Auth: يلزم إيقاف الكتابة والظهور، تسوية الوقت عند cutoff، وإنهاء العضويات وفك مراجع المضيف/Run المؤجلة بترتيب Account→Rooms/Runs، ثم حذف البيانات الخاصة. يُختبر ذلك مع عضو ومضيف ومالك فعليين ومع عملية متزامنة.
- **التصدير:** بيانات الطالب وحده، دون بريد أو سجل الآخرين أو محتوى إشراف داخلي. رابط مصرح قصير العمر، artifact ينتهي، وحالات Processing/Ready/Expired/Failed قابلة للتحقق؛ لا ملف دائم في ذاكرة Worker.
- **الاستعادة:** tombstones للحذف والسحب لا تُستعاد من snapshot القديمة وحدها. بروتوكول إعادة تطبيقها واختبار الاستعادة المعزول ضمن B7؛ إنشاء نسخة احتياطية ليس إثبات نجاح الاستعادة.
- **الحدود:** لا كود هاتف، ولا خدمة مدفوعة أو إطلاق تسجيل عام ضمن إنجاز محلي. الاختبارات البشرية والاستضافة الفعلية تُسجلان بدليلهما أو كحدود متبقية.

## أدلة الإغلاق

ربط AC05 وSC01–SC05 وLB01–LB04 وCM01–CM02 وOP03 وAC03/AC04 بحالات مستقلة وأدلتها. تشمل السيناريوهات حسابين على المتصفح نفسه، حذفًا أثناء روم نشطة، رفض IDOR والتصدير الأجنبي، سحب الإذن أثناء استجابة قديمة، إكمالًا عند حد أسبوع، نشرًا بعد تعديل الأصل، وترقية ذات mapping غير محسوم. التنفيذ والنتائج الفعلية ستُسجل في `docs/evidence/B6.md` عند بدء المرحلة.
