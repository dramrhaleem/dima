## أحدث تحقق — هجرة 031 وواجهة الانضمام

نجح البناء الحالي `dc5e818e939acaa2cef7dffae0be302df1b98c9c9626ae6c38abbdcc610fcd23` وفحص الأنواع وESLint و183 اختبارًا في19 ملفًا. اجتازت النسخة الحالية30 رحلة غرف في المتصفح دون تخطي أو إعادة تلقائية، و24 مجموعة API و9 مجموعات اتصال خاص. طُبقت هجرة031 بعد46 حالة مقارنة داخل معاملة متراجَع عنها؛ لم تتغير عتبات الحمل أو توزيعه. المرجع الجامع والبصمات: [التحقق الوظيفي الحالي](B5_POST031_FUNCTIONAL.json).

الإصلاحات تشمل رفض الردود السابقة لنسخة Time المقبولة حتى عندما بدأ الطلب قبلها، واستعلام العضوية الجماعي، وانتظار بيانات المؤقت عند أول انضمام مع شرح وإعادة محاولة، مع بقاء البيانات المقبولة قابلة للاستخدام أثناء التحديث الخلفي. فشل تشغيل المتصفح الأول قبل هذه الرحلات بسبب غياب البوابة المحلية؛ حُفظ تقرير الفشل وأُعيد الربط ثم أُعيدت اختبارات API والاتصال والمتصفح بنجاح.

نُقل مسار تخزين أدوات التطوير العامة بعد تحديث أعاد إنشاء المجلد السابق؛ حُفظت بصمات المحتويات والروابط وأدلة فشل المقارنة الأولي، وثبت أن اختلاف المحاولة اللاحقة محصور في حجم/حجز فهارس مجلدات Data2. نجح النقل والتحقق، والتوقف المؤقت للتطبيق نحو4.09ثوانٍ. [الدليل](B5_PUBLIC_RUNTIME_PARENT_RELOCATION.json). سبب ضغط القرص العابر الأقدم ما زال غير محسوم.

**المتبقي لإغلاق B5:** اختبار الدخول المتزامن الحالي، ثم7200ثانية فعلية لتوزيع4×20 مع20 تبويبًا ثانويًا ثم600ثانية لتوزيع8×10 مع20 تبويبًا. أي عينة انتقال تتجاوز2000ms تُفشل البوابة. لا يبدأ تنفيذ B6 قبل نجاحها. الأقسام التالية تحفظ التسلسل التاريخي ولا تُستبدل نتائج الفشل.

## التحقق الأولي — تاريخي

- فحص الأنواع وESLint ناجحان، ونجحت **108 اختبارات في 13 ملفًا** في تشغيل `pnpm test` بتاريخ 1 نوفمبر 2026. تشمل الاختبارات القديمة والجديدة؛ ليست 108 سيناريوهات غرف مستقلة.
- هجرات الغرف الخمس طُبقت في معاملة واحدة بعد إطلاق بوابة التطبيق من المراجع. [الإصدارات والبصمات](B5_MIGRATION_APPLY.json). بصمتا هجرتي B4 بقيتا كما هما. أي تعديل SQL لاحق يكون بهجرة إضافية.
- أُخذت نسخ gzip خاصة من قاعدة البيانات والأدوار قبل إعداد Realtime وقبل تطبيق الغرف، وتحقق فك الضغط. هذا ليس اختبار استعادة؛ اختبار الاستعادة الكامل ضمن B7.
- Supabase Realtime الرسمي `v2.143.3` يعمل محليًا بصورة Docker مثبتة بالبصمة، مع 91 هجرة داخلية. يستخدم PostgreSQL الحالي دون استبدال بياناته. الإعداد `private_only=true` و`presence_enabled=false`، وحد الاتصالات المكوَّن 200 وقناة واحدة لكل عميل؛ هذا **إعداد وليس قياس سعة ولا إثبات حد ذري صارم**.
- [اختبار النقل والإعداد](B5_REALTIME_TRANSPORT_RESULTS.json): WebSocket صحيح 101؛ مفتاح غير صالح 401؛ Origin غير معتمد 403؛ مسارات إدارة الخدمة غير مكشوفة عبر البوابة 404؛ نشر العميل مرفوض 403؛ نشر الخادم مقبول 202. اشتراك SDK الفعلي بقناة خاصة باستخدام المفتاح العام فقط يصل إلى رفض القراءة المتوقع.
- البوابة المحلية تنقل WebSocket إلى الخدمة الرسمية؛ لا تنفذ بروتوكول غرف مخصصًا. لا تعرض API إدارة Realtime، ولا تمرر Cookie التطبيق إلى اتصال WebSocket.
- التوقيع يستخدم مفتاح المشروع الحالي دون تدويره؛ الرمز بلا `sub`، بدور `anon`، ومحدد بالعضوية والغرفة والجيل. صلاحيته لا تتجاوز دقيقتين أو انتهاء المقعد، مع `jti` جديد عند كل إصدار. اختبار التوقيع يستخدم تحقق HMAC مستقلًا. التحقق الفعلي مثبت في اختبار الصلاحيات أدناه.

## API والاتصال الخاص

- بناء Next/OpenNext نجح، والمعاينة المحلية الحالية تشغل ملفات B5. اختبار الغرف الفعلي على هجرة 028000 اجتاز **24 مجموعة متطلبات بلا فشل**: سباق المقاعد، الدخول المتأخر، انتهاء المقعد، التحكم وتصحيح الانقطاع، الإشراف، الانتقالات الذرية، حدود الوقت، الأرشفة، تعارض حفظ بروفايل B1، واستعادة المهام والبث بعد فقد الإقرار، ورفض الحسابات الناقصة/غير المكتملة عبر HTTP وRPC دون آثار جانبية. [التقرير](B5_ROOMS_API_RESULTS.json).
- [اختبار Realtime الخاص](B5_PRIVATE_REALTIME_RESULTS.json) اجتاز **9 مجموعات** عبر Auth/PostgREST والخدمة الرسمية وعميل التطبيق: اشتراكان مصرحان واستلام بيانات phase/version/count فقط؛ رفض الغرفة والجيل الخطأ ورمز Auth العام؛ رفض رمز الغرفة في Auth وREST وAPI الحساب؛ منع النشر عبر HTTP وWebSocket مع رفض صريح وعدم وصول تحديث مزيف؛ استعادة CLOSED؛ إلغاء الوصول بالحظر وتجديد الرمز؛ وانتهاء المقعد.
- سياسة القناة تُراجع عند الاشتراك وتجديد رمز مختلف؛ لا ندّعي فحص RLS المستمر على كل رسالة. الرمز محدود بدقيقتين، ومحتوى البث مجرد بيانات عامة مختصرة؛ بيانات الأعضاء الخاصة تعيد التحقق مع كل قراءة HTTP.
- أثناء التشغيل ظهر تعارض اسمي SQL في بدء الدورة وفي تعليق الغرفة؛ أصلحهما إصداران إضافيان بعد مراجعة مستقلة، مع بقاء بصمات الإصدارات المطبقة سابقًا كما هي. [سجل التصحيحات](B5_MIGRATION_FIXES.json).

## تصحيحات أثناء المراجعة

المراجعة المستقلة عالجت قبل التطبيق ترتيب أقفال التسوية والإزالة، وأرشفة الغرف عند تأخر المهام، وقبول نقل الاستضافة بعد الحظر، وعدد الغرف المفتوحة، وشرط موعد جلسة الغرفة، ومنع خروج قديم من غرفة من إنهاء جلسة فردية أحدث. اجتاز اختبار API الفعلي 23 مجموعة متطلبات، بما فيها هذه المسارات. [النتيجة](B5_ROOMS_API_RESULTS.json).

في SDK، `CLOSED` يزيل القناة؛ تجديد الرمز وحده لا يعيدها. المصدر الآن يعيد إنشاء الاتصال بعد جلب صلاحية جديدة، ويتجاهل ردود الاتصال القديم. اختبار الوحدة والخدمة الفعلية يثبتان الإغلاق بانتهاء رمز قصير العمر ثم استعادة الاتصال بصلاحية جديدة واستلام تحديث لاحق.

أول تهيئة Realtime كشفت صلاحيات ناقصة لملكية المخطط و`log_min_messages`؛ عُدلت منح الأدوار المحلية المحددة، ثم اكتملت الهجرات. لم يُمنح دور الخدمة `SUPERUSER` أو `CREATEDB` أو `CREATEROLE`. تعطيل seed المعتاد يحافظ على إعداد القنوات الخاصة. [إعادة التشغيل الفعلية](B5_REALTIME_RESTART_RESULTS.json) أثبتت بقاء هوية المستأجر وإعدادات الخصوصية دون إعادة تهيئة.

## موارد الجهاز

كانت مساحة القرص الأساسي لا تكفي للصورة الرسمية. حُفظت صورتان عامتان غير مرتبطتين بأي حاوية، PostgreSQL القديمة وGitleaks، كأرشيفات على Data2 قبل إخراجهما من مخزن الصور. تحقق SHA-256 لكل blob ووجود manifest الأصلي ونجاح `docker image load`، ثم إعادة جرد الصور والحاويات ووحدات التخزين. بقيت الحاويات ووحدات البيانات الأخرى كما هي. أوامر الاستعادة والبصمات في ملفات JSON المجاورة داخل `/media/amro/Data2/dima-local-runtime/archived-docker-images`.

نُقلت بيئة Python المؤقتة الخاصة برسم هوية ديمة إلى مجلد الاعتماديات على Data2، مع التحقق من 2400 ملف/رابط والإبقاء على المسار القديم برابط رمزي. لم تُنقل الأسرار أو قاعدة البيانات إلى NTFS. قياسات الحمل يجب أن تسجل ضغط الذاكرة والمساحة الفعليين؛ هذه التهيئة ليست دليل أداء.

نُقلت لاحقًا بيانات وصفية لكاش **52 حزمة npm عامة محددة بالاسم** إلى Data2، مع فحص هوية كل حزمة وSHA-256 والإبقاء على كل مسار أصلي برابط رمزي. حُفظت 205,319,372 بايت وارتفعت المساحة المتاحة إلى نحو 300MB؛ لم تُنقل شجرة كاش عشوائية أو بيانات شخصية أو أسرار. [فحص المسارات وسجلا الاستعادة](B5_LOCAL_RESOURCE_HEADROOM.json).

## تشخيص وصول التحديثات

رُصدت رسالة ChannelRateLimitReached مرة لكل اتصال. مراجعة [المصدر الرسمي المثبت v2.143.3](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime_web/channels/realtime_channel.ex#L658-L673) أثبتت أن الخدمة تسجلها عند **قبول** آخر قناة مسموحة؛ ليست دليل رفض الاشتراك. التتبع المعزول أثبت join واحدًا لكل من SDK وWebSocket المباشر، مع استقبال التلميحات وتجديد الرمز. [دليل البروتوكول المنقّح](B5_ROOM_WIRE_010e9ba3-5f35-4d12-a56b-bc73a4e9a761.json). لم تُرفع حدود الخدمة. سبب مهلات التسليم ما زال قيد القياس عبر مراحل claim/publish/ACK، وليس محسومًا بهذه الرسالة.

الاختبار التشخيصي التالي توقف أثناء الإعداد وفشل: 7 أخطاء HTTP في 2309 طلبات، دون زيادة في deadlock. سجلات PostgREST تضمنت ثلاث مهلات انتظار مجمع الاتصالات؛ وسجل ناشر التحديثات ثلاث عمليات claim فاشلة قرب 5.255 ثانية، بينما بلغ أقصى publish ناجح 220ms وأقصى ACK ناجح 4766ms. الكود الفارغ لخطأ العميل لا يثبت بأثر رجعي نوع AbortError؛ القياس يضع التأخير في مسار التخزين/النقل إليه، ولا يعزل المعالج عن الأقفال. تنظيف موارد الاختبار اكتمل. [التقرير الفاشل المحفوظ](B5_ROOMS_LOAD_PROBE_b7cfc405-050e-4438-b132-75d4cf0a9786.json)، [السجل المنقّح](B5_HINT_DELIVERY_DIAGNOSTICS_b7cfc405.json).

كشف التدقيق فجوة في أداة القياس: مهلة انتظار التلميح كانت تُفحص في المرحلة المستقرة فقط. أصبحت تُفحص أثناء الإعداد أيضًا، وبوصول الرسالة قبل إزالة انتظارها؛ تظل مهلة 10 ثوانٍ نفسها، ولا يمحو الوصول المتأخر إخفاقًا سابقًا. هذا تصحيح اختبار، وليس إصلاحًا مثبتًا للخدمة. يجري أيضًا تدقيق تسلسل الطلبات مقابل العميل الحقيقي؛ لا يجوز حذف قراءات المحاكي دون تمثيل تحديثات الحالة والطلبات الشرطية التي تنفذها الواجهة.

مراجعة المصدر أثبتت مسارًا مستقلًا لتعطل التسليم السريع: يصل تحديث أحدث أثناء الإرسال الثاني، فلا يطالب به منتج آخر لأن lease مشغولة، ثم يخرج المرسل عند حد المحاولتين ويتركه للموزّع الدوري. الإصلاح الجاري يجمع طلبات الإرسال، ويتابع وفق نتيجة ACK ذرية، بميزانية زمنية محدودة مع إبقاء outbox الدائم. احتمال التزام claim بعد انقطاع رد العميل يحتاج اختبارًا مستقلًا؛ لم تثبته السجلات الحالية. لا يُعد هذا الإصلاح مكتملًا قبل بناء النسخة وتحققها.

طُبقت هجرة `029000` بعد نسخ قاعدة البيانات والأدوار والتحقق من gzip وبصمات 11 ملفًا سابقًا. البناء المراجع نجح، ونجح فحص الأنواع وlint و127 اختبارًا في 15 ملفًا، بينها اختبارات منسق الإرسال ومحاكي العميل. [سياسة الإرسال وحدودها](B5_HINT_PRODUCER_POLICY.md) تصف حد مهمتين متزامنتين و32 مفتاحًا وميزانية 28 ثانية، مع الاستعادة الدائمة عند الخطأ أو استنفاد الميزانية؛ ليست ضمان وصول خلال 10 ثوانٍ أثناء تشبع التخزين.

التحقق الفعلي بعد البناء اجتاز [خمس مجموعات](B5_HINT_PRODUCER_b38ea877-7c7d-49cf-b7a7-4929d0c6baf3.json): صلاحيات ACK وأسوار النسخ، handoff، إلغاء SQL تحت قفل فعلي خلال 2224ms دون تغيير lease، استعادة فقد رد **محاكى**، وثمانية أوامر متزامنة في أربع غرف على workerd مع وصول آخر نسخة دون موزع دوري. ذلك يثبت الحالات المحددة، لا السعة الكاملة. مهلة العميل للموزع المحلي أصبحت 45 ثانية بدل 15 حتى لا تقطع مهمته ذات ميزانية 28 ثانية مسبقًا؛ لا تدعي أن أسوأ دفعة تخزين تنتهي حتمًا داخل هذا الحد.

مراجعة [مطابقة الحمل للواجهة](B5_WORKLOAD_FIDELITY.md) أثبتت أن النموذج السابق يضيف قراءات ويغفل أخرى، ولذلك لا يُعد مطابقًا ولا حدًا أعلى مثبتًا. نتائج النسخة المقبلة تحمل نموذجًا جديدًا؛ لا تُنسب فروقها كلها إلى سرعة SQL. أداة مراقبة قاعدة البيانات الجديدة تسجل عينات مجمعة للانتظار والتنفيذ عبر اتصال قراءة مستقل، دون نص SQL أو هوية أو مفاتيح؛ ليست قياس CPU ولا ترى صف انتظار PostgREST خارج المجمع.
