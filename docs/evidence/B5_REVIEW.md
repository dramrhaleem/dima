## Design boundaries to resolve before implementation

1. **Central ledger reuse:** Room participation references central TimeSessions; no separate room counter. Unique user/run/round identifies a Participation, which may have multiple sequential Sessions after Finish and a fresh Join in the same round. Resume retains the original room-round deadline; B4 Solo's shifted deadline is not the room policy. A paused room Session finalizes when the round ends.
2. **Locks and atomic switching:** Personal commands lock Account, then all required Room IDs in stable order, then Runs in stable order. New capacity/access is checked before ending old membership/time. Failed Solo→room, room→room or room→Solo leaves prior state intact. Remove/ban/suspend cannot lock Room and then wait for other Accounts; committed effective cutoffs plus independent account-first settlement must make immediate reads truthful.
3. **Three independent concepts:** seat membership, presence control and accepted time must remain separate. Presence renews every 30 seconds; display changes at 90 seconds, host eligibility at 120, seat/roster expiry at 180. Expiry does not close an accepted Session or revoke its valid time. Rejoin after expiry is explicit, rechecks capacity and reuses an existing same-round active Session. A different-room switch must account for old accepted time even after its seat expired.
4. **Device control coherence:** Explicit room-control transfer must reject old presence renewal and old room-time control without breaking the owner's ability to finish already accepted time after membership expiry. The central time claimControl/resume/renew paths require review; a new room endpoint alone cannot close a bypass.
5. **Host lifecycle:** Host claim is atomic after the server-observed absence threshold; current membership/lease determines eligibility. Transfer requires target acceptance. The current host exists in Lobby as well as Run. Leaving does not stop the run; return does not reclaim a transferred role.
6. **Visibility and moderation:** The public projection has metadata/counts only. Join explicitly acknowledges limited name/status visibility and starts Watching, not time. Roster reads are viewer-filtered for current membership and bilateral Block; task titles, plans, emails and progress do not enter shared DTOs. Reports protect reporter identity. Host removal is run-scoped, owner ban is room-scoped, platform suspension is privileged and audited. Block does not promise expulsion from a public room.
7. **Replay and broadcast:** Durable receipts contain operation metadata, never a saved roster. Current access gates replay and snapshots. Realtime is invalidation only, with phase/version/count payloads; no raw profile or membership records. Old sockets cannot obtain new private data after removal/expiry.
8. **Lifecycle deadlines:** A run includes four focus rounds, intervening short breaks and its final long break. Joining a round is always explicit. Close prevents new entry/start immediately but lets the current finite run finish. Suspension stops it at a server cutoff. Archive requires seven days of inactivity, no active run and no live membership; delayed jobs never extend runs or retain phantom seats.
9. **Practical resource boundary:** Bounded renewals must not generate a room-wide event every 30 seconds. At 80 members across four full rooms, 120 renewals per hour and 20 recipients imply 192,000 deliveries/hour before other traffic; daily two-hour use would exceed 11 million deliveries in 30 days. Measure actual deliveries, snapshots, connections and CPU. A reduced local probe is not equivalent to the canonical sustained gate.

These are review constraints communicated to implementation owners, not claims of implemented behavior. Proposed contracts and SQL will be reviewed as they land.

## Minimum schema/API direction

Reuse B4 TimeSession/Interval/Correction, idempotent command semantics and cutoff settlement. Add room metadata/policy, versioned membership with presence generation, immutable run settings/deadlines, unique participation and links to sequential sessions, host-transfer intent, room bans, bilateral user blocks, restricted reports/moderation audit, and durable room invalidation/settlement jobs as needed. The physical table split remains an implementation choice; each invariant must have a transactional owner.

Keep public directory/detail separate from member snapshots and own time. Required mutations include create, visibility-acknowledged Join/Rejoin, presence renewal/control transfer, Leave/switch, StartRun, JoinRound, host offer/accept/claim, owner settings/Close, Remove/ban, Block/report and privileged suspension. Private operations derive actor identity from authenticated context; service writes are narrow and roles cannot come from editable profile metadata.

## Pinned Realtime setup review — 1 November 2026

This is read-only source research for `supabase/realtime:v2.143.3`, alongside the current local Compose file. No service, database, container or volume was changed by this reviewer. The integrating owner reports preserving the unused official Postgres image archive; this review does not independently attest its contents.

**JWT boundary.** The pinned connection verifier requires `role` and `exp`, not `sub`; authorization context explicitly permits a nil subject. The proposed room-only token can therefore omit `sub` and use signed membership/generation claims with `role=anon`. Add `iat` and a short expiration. A claim is not authorization by itself: room RLS must check the signed issuer/audience, topic, membership generation, current lease and room restriction. Source: [connection verifier](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime_web/channels/auth/channels_authorization.ex), [authorization context](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime/tenants/authorization.ex).

**Refresh is real reauthorization, but not continuous reauthorization.** A changed access-token message clears cached policies, rebuilds the context and reruns DB read-policy authorization; revoked read permission closes the channel. Identical tokens are ignored, rapid refresh is throttled, and ordinary expiry confirmation does not reread RLS. Issue genuinely fresh tokens and test lease/generation revocation on refresh. Keep broadcasts free of names regardless of socket state. [Pinned channel implementation](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime_web/channels/realtime_channel.ex).

Global `JWT_CLAIM_VALIDATORS` also applies to HTTP tenant authentication through the same verifier. Do not globally require `role=anon` if server publishing uses a service-role token. Shared `aud`/`iss` validators can restrict the dedicated tenant; enforce browser read-only access in RLS, with no anon INSERT policy. Confirm publisher and browser paths independently. [JWT configuration](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime_web/channels/auth/jwt_verification.ex), [HTTP authentication](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime_web/plugs/auth_tenant.ex).

**Database prerequisites.** Broadcast-only use still starts the tenant's replication connection. It uses built-in `pgoutput` for `realtime.messages`, a temporary logical slot and a publication; this path does not require wal2json. Enable logical WAL with available sender/slot capacity. No need to replace the existing PG17 data volume with a Supabase image merely for these primitives. [Tenant connection startup](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime/tenants/connect.ex), [broadcast replication implementation](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime/tenants/replication_connection.ex).

A least-privilege candidate for runtime is a dedicated `supabase_admin` login with `REPLICATION`, but without SUPERUSER/CREATEDB/CREATEROLE; ownership/DDL rights restricted to `_realtime` and `realtime`, membership in `supabase_realtime_admin` for message ownership/partitions, permission to SET ROLE anon, SELECT on `realtime.schema_migrations`, and database CREATE for the publication. This is an inferred grant set to validate locally, not a proven migration recipe. Bootstrap/upgrade may run separately under the existing local migrator. Do not give runtime unrelated application-table privileges. PostgreSQL requires replication privilege for streaming and database CREATE/table ownership for publication management. [PostgreSQL17 privileges](https://www.postgresql.org/docs/17/logical-replication-security.html), [publication rules](https://www.postgresql.org/docs/17/sql-createpublication.html).

Precreate the named roles deliberately: tenant migration history references `dashboard_user` and `supabase_admin`; `supabase_realtime_admin` owns realtime objects. The PG17 dump bootstrap contains conditional grants `GRANTED BY supabase_admin`; a restricted bootstrap must either precreate the intended roles/grants or use a migrator authorized for that grantor. Runtime creates date partitions and assigns their ownership to `supabase_realtime_admin`. Keep schema-migration permissions intact for its readiness probe. [Restriction migration](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime/tenants/repo/migrations/20260707120000_restrict_realtime_schema.ex), [default grants migration](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime/tenants/repo/migrations/20260914120000_delegate_messages_grants_to_postgres.ex), [PG17 dump](https://github.com/supabase/realtime/blob/v2.143.3/priv/repo/tenant_db_dump_17.sql), [partition creation](https://github.com/supabase/realtime/blob/v2.143.3/lib/realtime/tenants.ex).

A narrow stable helper can return the transaction's `request.jwt.claims` JSON, with schema usage/function execution granted only as required. It must not fabricate an authenticated subject for the no-sub room token. Existing `auth.uid()` should remain null for that token.
