# B0 — دليل قاعدة البيانات والمصادقة المحلية

التاريخ: 31 أكتوبر 2026. الحالة: **اختبار محلي فعلي ناجح** لمجموعة مصغرة من Supabase؛ ليس إعداد حساب مستضاف أو تدقيق أمان إنتاجي.

## ما نُفّذ

- PostgreSQL 17 Alpine في حاوية Dima مستقلة؛ GoTrue v2.197.0 للمصادقة الفعلية وPostgREST v14.18 للقراءة/الكتابة. الصور مثبتة بالـdigest في compose.
- gateway محلي على `127.0.0.1:54321` يوفّر مسارات Supabase القياسية، بلا خدمة عامة أو DNS.
- migration لإنشاء `foundation_checks` مع FK إلى مستخدم Auth وقيود طول النص وRLS للمالك SELECT/INSERT فقط. الجدول دليل B0 ويُزال قبل النشر العام؛ ليس سجل تقدم أو وقت.
- bootstrap roles وauth schema ودالة `auth.uid()` المحلية. يجري Auth ترحيلاته الأصلية، وتُطبق migration التطبيق في معاملة مع سجل خاص يمنع إعادة تطبيقها.
- start/stop قابلان لإعادة التشغيل، وبيانات PostgreSQL محفوظة بعد الإيقاف. لا أمر reset أو حذف أُضيف.
- credentials محلية عشوائية وfixtures صناعية محفوظة خارج Git؛ لا service-role key ضمن بيئة العميل، ولا طباعة لرموز الدخول.

## التحقق المنفّذ

الأوامر من جذر المشروع:

```bash
node scripts/local-backend/start.mjs
node tests/backend/verify.mjs
```

نجحت 11 حالة تكامل بعد تشغيلها على الخدمات الحقيقية:

1. إصدار/تجديد جلسات فعلية لحسابين صناعيين ثم التحقق من هوية المستخدم عبر Auth.
2. رفض token غير صالح.
3. INSERT للمالك محفوظ في PostgreSQL.
4. SELECT للمالك يعيد السجل المحفوظ.
5. حساب آخر لا يرى السجل حتى بمعرفة UUID.
6. رفض INSERT يزوّر owner_id لحساب آخر.
7. رفض القراءة المجهولة.
8. قيد طول label على مستوى DB.
9. رفض UPDATE غير الممنوح، حتى للمالك.
10. UUID مكرر لا ينشئ سجلًا ثانيًا.
11. رفض Origin غير مدرج في gateway المحلي.

نجح تشغيل start مرة أخرى دون reset، وأُعيد الاختبار باستخدام الحسابين الموجودين مع password login؛ البيانات السابقة لم تُمحَ. بعد إضافة أصل العميل المنفصل على المنفذ 4174، أُعيد تشغيل gateway وحده والتحقق: 11 ناجحة، صفر فاشلة. هذا لا يشمل اختبارات التطبيق التي يجريها المسار الرئيسي.

رصد نقطة زمنية واحدة بعد التشغيل: ذاكرة حاويات db/auth/rest تقريبًا 18.25/14.02/17.73 MiB؛ ليست benchmark حمل أو وعد استهلاك. كل المنافذ المنشورة loopback، والتحقق الفعلي للصلاحيات: مجلد runtime هو 0700 والملفات الثلاثة الخاصة 0600.

## المشكلة التي حُلت والحدود

Data2 نظامه fuseblk/NTFS، ويعيد ملفات الدليل إلى 0777 ولا يتيح ownership/chmod المطلوبين لـPostgreSQL. محاولة initdb الأولى توقفت قبل إنشاء قاعدة سليمة. نُقل التخزين إلى volume جديد خاص بـDima على نظام Linux، والأسرار إلى `~/.local/state/dima-b0`؛ حُذفت فقط ملفات credentials التجريبية التي أنشأتها هذه المهمة على NTFS. لم تُمس بيانات مشروع آخر. استُكملت تهيئة role search_path إلى auth بعد أن كشف التشغيل الأول صلاحية public غير المناسبة؛ ملف bootstrap أصبح يحتوي التصحيح.

هذه مجموعة محلية مصغرة **وليست CLI Supabase كاملًا**: لا Realtime أوStorage أوStudio أوSMTP أوGoogle OAuth. autoconfirm محلي، ويجب ألا ينتقل إلى الإنتاج. لا تحقق من Hosted Supabase أو Workers البعيد أو إرسال البريد. التشغيل الكامل من قاعدة نظيفة جديدة بعد التصحيح لم يُعد باختبار حذف البيانات؛ بدء الخدمات على البيانات الموجودة والاختبارات نجحا. يظل اختبار إعادة إنشاء/استعادة مستقل مطلوبًا قبل B7.

الملفات: `scripts/local-backend/`، `supabase/migrations/20261031180000_foundation_checks.sql`، `supabase/seed.sql`، `tests/backend/verify.mjs`. دليل التشغيل في `scripts/local-backend/README.md`.

المصدر الرسمي الذي راجعناه لاختيار Auth/REST وبيئة التشغيل: [Supabase Docker configuration](https://github.com/supabase/supabase/blob/master/docker/docker-compose.yml). لا ننسخ خدمة gateway الإنتاجية؛ Router Node هنا محدود ومحلي فقط.

## تحقق مسار الدمج النهائي

بعد إضافة السماح بترويسة Supabase SDK `x-supabase-api-version`، أضاف مسار الدمج حالة preflight للتحقق منها، وشغّل مجموعة الباك إند: **12 ناجحة**. الأعداد 11 أعلاه تصف الجولة السابقة وليست النتيجة النهائية. اختبارات API والمتصفح منفصلة في [دليل B0](B0.md).
