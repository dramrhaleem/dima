# B7 free-tier feasibility — planning draft

**Checked 2026-11-01; planning only.** The user selected Cloudflare Workers + Supabase Free for approximately 50–100 users; registered users, daily active users, concurrent accounts, and browser connections are different denominators. No hosted capacity, free-operation guarantee, B5 acceptance, deployment, paid service, implementation, or cadence change is established by this note. Current v4/new UI and representative real enrollments remain unmeasured here. Complete B5 under its existing acceptance contract before later optimization work.

## Current official limits

- Workers Free: 100,000 requests/day/account, resetting at midnight UTC; 10ms CPU per HTTP invocation. Waiting for network/DB is not CPU. Local response latency and process CPU are not hosted invocation CPU evidence. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).
- Direct static-asset requests are free/unlimited; SSR and requests invoking Worker code count. Existing `apps/web/wrangler.jsonc` already has the `ASSETS` binding; prove actual routing rather than assume an additional Pages project is necessary. [Static assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/).
- Supabase Free: 500MB database, shared CPU/500MB RAM, 5GB uncached egress/month and a separate 5GB cached allowance. The cached allowance is not extra database/API egress. Egress includes Database, Auth, Storage and Realtime outbound traffic. [Pricing](https://supabase.com/pricing), [egress accounting](https://supabase.com/docs/guides/platform/manage-your-usage/egress).
- Realtime Free: 200 concurrent connections, 100 messages/sec, 100 channel joins/sec, and 2 million messages/month. Broadcast billing includes publisher plus receiving subscribers; application hints and raw WebSocket frames are not interchangeable billing units. [Realtime limits](https://supabase.com/docs/guides/realtime/limits), [message accounting](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages).

## Retained measurement and explicit scenarios

The measured `steady-4x20` window ran from `2026-11-01T05:24:57.929Z` to `2026-11-01T05:50:24.640Z`: **1,526.765937s**, **100 foreground connections / 80 controller accounts + 20 secondary read-only connections**, **12,118 HTTP requests**, **58,187,136 browser-received HTTP response-body bytes**. The run was interrupted: `completed=false`, `acceptanceEligible=false`. It is a retained planning sample, not completed sustained-load acceptance or current-v4 evidence.

Synthetic accounts had **no enrollments**, chose Work without a linked activity, and used four rooms of twenty memberships. HTML/assets and cookie-auth shell startup were excluded. Linear repetition of this same cohort gives approximately 28,573 HTTP requests and 137.20MB browser response bodies per active hour:

| Same cohort active hours/day | HTTP requests/day | Browser response bodies over 30 days |
|---:|---:|---:|
| 1 | 28,573 | 4.12GB |
| 2 | 57,147 | 8.23GB |
| 4 | 114,293 | 16.46GB |

These are assumptions, not observed user demand or billing. HTTP totals include dispatcher calls during the active measurement. If the same 30s dispatcher runs all day, add approximately 2,760 / 2,640 / 2,400 inactive-hours calls respectively. Other routes, startup, users, retries and B6 operations need additional budget. Without those additions the measured cohort reaches 100k requests at about 3.50 active hours/day and the existing 70% warning threshold at 2.45 hours/day. Peak concurrency affects bursts; cumulative active connection-hours affect daily/monthly consumption. Smaller rooms change snapshot size, so bytes do not necessarily scale linearly with headcount.

**Browser bytes are not billed Supabase egress.** The harness measures Worker-to-client response bodies, not all Supabase-to-Worker DB/Auth responses or provider accounting. Some response content is generated by Workers; upstream requests may add unseen bytes. Room snapshot and command handlers largely forward RPC JSON, making the volume a material warning, not proof of a quota breach. At the two-hour request projection, 5GB would permit roughly 2.9KB Supabase egress/API request if it were the only usage; actual provider bytes, realistic learning payloads, Realtime and other traffic must be measured.

The same window delivered 2,500 application hints: approximately 354k received hints/month at two active hours/day. Publisher messages, retries, provider accounting and peak-second fan-out remain separate proof obligations; connection headroom alone proves neither throughput nor monthly fit.

## Current-source cadence and later proof

`packages/ui/src/rooms-provider.tsx` currently renews foreground controller presence every 30s and then fetches a snapshot; secondary live tabs poll snapshots every 30s. `apps/web/src/server/realtime-token.ts` caps token life at 120s; the client refreshes 15s early. For 80 controllers/20 secondary tabs, uncomplicated nominal traffic is approximately `80*2*120 + 20*120 + 100*3600/105 = 25,029 requests/hour`, before hints, boundaries/actions and dispatch. This is a cadence estimate, not a strict floor: reads coalesce, busy ticks can skip, and seat-limited grants/retries can add traffic. The displayed one-second clock is local. v4 changes Time reconciliation but does not remove the unchanged baseline cadence; its measured result is pending.

Concrete later B7 release proof:

1. Retain Workers + Supabase and D1 only for the approved encrypted privacy ledger; no migration to a second room backend. Validate direct static-asset routing and measure hosted CPU per relevant route, including SSR/auth, learning/planner, dispatch and privacy encryption.
2. Declare expected daily active users, foreground hours and multi-tab ratio; measure current v4/new UI with representative enrolled courses/history, full browser startup, round boundaries and reconnect bursts. Record exact denominators and versions.
3. Reconcile actual Workers daily requests and Supabase DB/Auth/Realtime egress with provider usage; verify database growth, monthly messages and peak-second messages/joins. Retain the existing 70% warning and no automatic paid upgrade.
4. If evidence requires reduction, first assess compact/paginated payloads and duplicate reads. A smaller browser response does not save Supabase egress if the Worker still fetches full DB state. Combining renewal/snapshot or changing cadence would require separate authorization/implementation and regression evidence preserving security, freshness, leases and recovery; it is not a change to B5 acceptance.
5. Preserve B6/OP02 Prepare → external acknowledgment → apply and fail-safe Pending behavior. B7 still requires real D1 append/read/retry/replay, independent backup/inventory/key recovery, and isolated restore proof under `PRIVACY_LEDGER_CONTRACT_AR.md`. D1 Free includes 5m rows read/day and 100k rows written/day, but quotas do not prove restore correctness. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).

**Decision:** keep the chosen free-first stack and existing quality gates. Free operation remains conditional on measured usage and hosted CPU/egress proof, not merely the label “50–100 users.”
