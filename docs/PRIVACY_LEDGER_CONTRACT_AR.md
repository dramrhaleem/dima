# ملحق معتمد: سجل الخصوصية وحد الاستعادة

**1 نوفمبر 2026 — قرار تقني معتمد للتنفيذ، غير منفذ أو مستضاف.** هذا الملحق هو المرجع الحاسم لترتيب الحذف/السحب والاستعادة في B6/B7، ويتقدم في هذا النطاق على المقترحات السابقة. لا يبدأ تنفيذ B6 قبل إغلاق B5. الاختيار ضمن تفويض المستخدم اختيار أفضل تنفيذ ويب؛ لا يتضمن إنشاء خدمة خارجية أو شراء أو نشر.

## 1. القرار وحدوده

- تبقى بيانات المنصة وAuth وRealtime في **Supabase**، والواجهة والـAPI على **Workers**. الاستثناء الوحيد من عبارة عدم نقل البيانات إلى D1: قاعدة **D1 مستقلة على Free** لسجل الخصوصية المشفّر التقييدي خارج نطاق نسخة Supabase. لا نقل لبيانات التعلم/الوقت/الغرف، ولا Durable Objects أو sockets إضافية.
- **adapter D1 واحدة محليًا ومستضافًا**: محليًا binding تحاكيها Wrangler/Miniflare مع persistence خاصة خارج نسخة Supabase؛ مستضافًا D1 primary دون Sessions API. `append(operationId, ciphertext)`, `readAfter(sequence)`, `head()` تبقى العقود نفسها، وAEAD على مستوى التطبيق في البيئتين. يُستبعد بناء journal/framing/fsync أو IPC مخصص؛ استمرار محلي عبر restart لا يثبت متانة الخدمة البعيدة أو نجاة فقد الجهاز.
- سجل append-only على مستوى التطبيق، وليس WORM. يحتفظ بأقل أثر لازم لسحب الوصول/الحذف؛ لا يسجل grants جديدة أو بيانات المستخدم التفصيلية. تشفير AEAD، operationId فريد وdigest، وإعادة نفس ciphertext في retries. duplicate مختلف المحتوى مرفوض؛ timeout نتيجة مجهولة تعالج بقراءة/retry مطابق.
- لا خدمة مدفوعة تلقائية. الحصة/الانقطاع يبقيان العملية Pending مع مراقبة وتشخيص؛ لا تجاهل acknowledgment لإبقاء الواجهة ناجحة. المقارنة والمصادر الرسمية في [بحث الخيارات](B6_PRIVACY_LEDGER_PROPOSAL_AR.md).

### 1.1 دليل إعادة الاستخدام وحد الدمج المحلي

فحص قراءة فقط في 1 نوفمبر: [scripts/worker.mjs](../scripts/worker.mjs) يشغّل `wrangler dev --local` داخل buildRoot الذي قد يكون mirror، بلا `--persist-to`. [wrangler.jsonc](../apps/web/wrangler.jsonc) لا يحوي D1 binding الآن. النسخة المثبتة 4.156.0 تدعم D1 محلية عبر Miniflare؛ مصدر CLI يختار `preview_database_id ?? database_id ?? binding` محليًا ويستخدم `getD1Database`، فلا يلزم إنشاء مورد بعيد لهذا المسار. تؤكد [وثائق D1 المحلية](https://developers.cloudflare.com/d1/best-practices/local-development/) إتاحة binding نفسها وعزل البيانات المحلية واستمرارها وتخصيص موضعها بـ`--persist-to`. هذا إثبات دعم وتصميم، لا اختبار تشغيل binding ديمة.

في B6 فقط: إضافة binding باسم `PRIVACY_LEDGER` بوضع محلي صريح `remote: false`، وتوحيد الهوية والمسار المطلق بين preview وأوامر schema المحلية `--local --persist-to`. المسار المقترح `.local/privacy-ledger-state` تحت جذر المصدر يُحل إلى absolute path، بصلاحيات POSIX خاصة ومجلد خارج build mirror ونسخ Supabase؛ لا الاعتماد على `.wrangler/state` الافتراضي الذي يتبع موضع config. schema وترحيلها مستقلان عن PostgreSQL. تحصل طبقة الخادم على binding عبر `getCloudflareContext().env` القائم؛ إعدادات `next dev` الحالية لا تُفترض موفرة لها، وغيابها يعيد عدم جاهزية بدل fallback إلى ذاكرة أو Supabase أو remote. إعادة التشغيل والنسخ المحلية تستخدم أداة المحاكي؛ لا تعديل مباشر لملفات SQLite الحية.

المفتاح خارج persistence والنسخ، ويضاف لاحقًا لمسار env الخاص المسموح في `scripts/worker-files.mjs` دون تسريبه للـmirror أو العميل. تظل AEAD/idempotency/Prepare→ack→apply واختبارات lost ACK وrestart وإعادة replay وحقن فشل التخزين مطلوبة؛ المحاكي لا يثبت quotas أو replication أو hosted durability. فصل المجلد عن نسخة Supabase ليس فصله عن عطل الجهاز، ولا يحل محل checkpoint/inventory الموثوقة في §3. لا تغيير فعلي للـbinding أو scripts أو migration أو runtime بهذا الملحق.

## 2. العقد الملزم للنجاح والفشل

1. **Prepare في PostgreSQL:** تحقق الهوية والصلاحية وrevision؛ الحذف يتطلب proof حديثًا مرتبطًا بالجلسة/التحدي، لا `iat` من refresh. تثبيت intent/outbox غير قابل لتبديل المحتوى، ومنع grant متعارضة. Pending يحجب البيانات محل السحب في كل قراءة/تفاعل محلي ويخفيها في واجهة صاحب الطلب؛ للحذف يمنع أيضًا الكتابات الجديدة. يظهر «جارٍ تأكيد الحفظ» دون Saved/Done. ما وصل مسبقًا إلى مشاهد بعيد يخضع لعقد إبطال العرض؛ لا ادعاء محو لحظي عن بعد.
2. **External acknowledgment:** إرسال intent المعتمدة إلى D1 وانتظار إقرار مطابق محفوظ. لا PostgreSQL lock/transaction مفتوح أثناء الشبكة، ولا purge نهائي قبل الإقرار. نفاد quota أو انقطاع لا يرفع الحجب الاحترازي، وتستأنف نفس operationId.
3. **Apply في PostgreSQL:** تثبيت receipt الخارجية وتطبيق revoke/cutoff الدائم ذريًا مع revision/receipt/invalidation. هنا فقط يسمح بإعلان نجاح حفظ السحب. بعد ذلك تسوية deletion وpurge وAuth cleanup بدفعات حسب ترتيب الأقفال الحالي؛ Done للحذف بعد اكتمالها كلها. وقت توقف النشاط الاحترازي المثبت في Prepare لا يولد وقتًا إضافيًا أثناء Pending.
4. **Crash/retry:** acknowledgment خارجية بلا apply بعدُ تُستأنف، وتعامل intent عند restore تقييديًا حتى إن غابت receipt النهائية من النسخة. Prepare بلا acknowledgment لا يُعلن مقاومًا للاستعادة؛ نسخة أقدم منه قد لا تعرف الطلب. لا نخلط هذا القيد مع سحب مكتمل. لا transaction موزعة ولا حذف tombstone لإلغاء أثرها.

كل سحب يحتاج منع إحيائه يدخل هذا المسار: grants والعلاقة والحظر وPeople/boards ومشاركة milestone وحالة المصدر بحسب صلاحيات المجال، إضافة إلى account deletion. إعادة opt-in لاحقة لا تمحو الأثر القديم. بعد restore يُطبق السجل التقييدي تحفظيًا، وتُطلب **موافقة جديدة** حتى لو تضمنت النسخة regrant أحدث؛ تعرض الواجهة أن المشاركة أوقفت احترازيًا بعد الاستعادة. لا يُبنى event store شامل للأذونات في هذا الإصدار.

## 3. ما تستطيع الاستعادة إثباته

**حد الضمان:** استرجاع Supabase قديمة مع بقاء سجل D1 الخارجي سليمًا ومتاحًا والمفاتيح صحيحة. لا ضمان ضد rollback/حذف D1 نفسها أو فقد كل مخازن الاسترداد. `head()` تقرأ ما يوجد الآن؛ لا تكشف وحدها أن عمليات أحدث غير معروفة فُقدت. التشفير وhash لا يمنعان truncation إلى prefix صحيح.

بوابة الصيانة/الفتح خارج Supabase المستعادة. أثناء cutover تُوقف أو تُصرّف الكتابات، وتُقرأ D1 primary حتى head مستقرة. يجري replay للتقييدات وإعادة الإسقاطات وفحص الوصول قبل الفتح. subject هو UUID وجيل الحساب، لا email. المفتاح المفقود أو payload غير مفهوم أو فجوة مثبتة يجعل البوابة مغلقة.

يلزم **checkpoint موثوق محفوظ في inventory الاسترداد خارج Supabase وD1**: هوية السجل/جيله، آخر sequence معروفة وdigest المرجعي وتاريخ الالتقاط، ومرجع نسخ الاسترداد. تطابق المورد مع checkpoint يكشف الرجوع قبل نقطة معروفة أو تبديل السجل؛ لا يثبت عدم فقد عمليات بعد آخر checkpoint إذا لم يوجد شاهد مستقل أحدث. لا يُستنتج «آخر نسخة مؤكدة» من المخزن الجاري فحصه وحده. حين يثبت اختلاف/فقد أو لا تتوفر معلومات كافية عن سلامة السجل بعد حادث D1، لا تفتح الخدمة باعتبار restore ناجحة؛ معالجة ذلك حادث استرداد مستقل. مكان inventory المستضافة ونسختها الموثوقة ومالك استردادها يُثبت قبل بوابة B7، وليس مجرد ملف داخل repo أو نسخة Supabase.

احتفاظ backup المستهدف سبعة أيام؛ tombstones لا تنتهي آليًا بعد سبعة أيام من الحدث. تبقى حتى انقضاء آخر نسخة قابلة للاستعادة قد تعيد البيانات/الإذن وكل restore معلقة، وفق inventory تشمل النسخ اليدوية. المدة غير المحسومة تعني استمرار الاحتفاظ بالحد الأدنى المشفر. سجلات checkpoint بلا محتوى شخصي زائد ومفاتيح فك التشفير منفصلة عن النسخ.

## 4. الإثبات المتبقي

- B6 محليًا: crash على حدود Prepare/ack/apply/purge، lost response، duplicate/mismatch، تعطل quota، pending deny مع concurrent grants، وعزل هوية/تصدير. لا إغلاق لأي بوابة استضافة بهذه النتائج.
- B7 مستضافًا: المورد والمفتاح والأذونات الفعلية، append/read/retry/replay، restore معزولة قبل intent وبعد acknowledgment، Auth وartifacts، opt-in جديدة، كشف rollback خلف checkpoint معروفة، وعدم ادعاء كشف عمليات مجهولة بعد checkpoint. يبقى unknown-tail loss حدًا معلنًا، لا اختبارًا يمكن تمريره بحيلة.
- غير المحسوم تشغيليًا: مكان backup/inventory خارج نطاق الفشل، مالك الاسترداد وإدارة المفاتيح، وإثبات مدد الاحتفاظ وRPO/RTO على الموارد الفعلية. لا خيارات منتج متشعبة؛ هذه شروط تشغيل مطلوبة قبل البيانات الحقيقية.
- SMTP الفعلي وتجربة المستخدمين البشر ومراجعة moderation وبقية بوابات الاستضافة مستقلة؛ لا تغلقها الاختبارات المحلية أو هذا القرار. لم يُنشأ مورد أو مفتاح أو binding ولم يحدث نشر.
